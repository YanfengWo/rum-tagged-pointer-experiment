# v0.1 Acceptance Boundary

Status date: 2026-06-13.

This document is the current stabilization boundary for the first usable
`v0.1` cut. It collects the public-contract decisions that were previously
spread across the architecture notes, `mma-hol` smoke notes, and Jupyter
migration audit.

`v0.1` is a kernel and host-contract stabilization cut. It is not a full CAS
release, a broad Wolfram front-end clone, or a polished notebook product.

## Product Boundary

The release target is a programmable symbolic core-language runtime with a
narrow host API and enough real downstream pressure to prove that the boundary
is usable.

The main acceptance surfaces are:

- the supported Wolfram-style core-language slice documented in
  [core-language-support-matrix.md](./core-language-support-matrix.md);
- the `rum-host` Rust embedding facade for sessions, requests, structured
  outcomes, failures, prints, messages, traces, input requests, inspect,
  completion, and completeness;
- `rum-cli` and `rum-repl` as developer tools for loading scripts, running
  probes, and debugging semantics;
- the `mma-hol` cold and stable-snapshot lanes as the main downstream pressure
  test;
- a `rum-host`-backed basic Jupyter Notebook tech preview.

Internal evaluator, matcher, cache, and representation details remain unstable
unless they are exposed through `rum-host`, documented CLI behavior, or the
core-language support matrix.

## Core-Language Contract

Same-name Wolfram-language behavior should be treated as a compatibility
commitment only where the support matrix marks the feature as implemented or
partial. Partial entries need documented limits. Planned, excluded, extension,
and deliberately divergent entries are not release promises.

New same-name breadth should be promoted only when at least one of these is
true:

- the support matrix already names it as part of the current core-language
  lane;
- `mma-hol` or another concrete downstream package is blocked on it;
- the missing behavior is needed to preserve an existing public host or CLI
  contract.

Resource limits, recursion limits, message behavior, held evaluation,
definition scoping, package loading, and suspend/resume flows are part of the
runtime contract when they affect the public request APIs.

## `mma-hol` Acceptance

`mma-hol` is the preferred real-project pressure test for `v0.1`. The target is
not to chase every Wolfram feature in isolation, but to make the `mma-hol` to
`rum-hol` migration path credible.

The current accepted lanes are:

- cold source loading and tests through the clean-clone core, Bool, Drule,
  Tactics, Printer, and Parser layers; the current clean-clone smoke results
  are core package load through Parser/Printer plus `bool_tests.wl`
  `List[73, 0]`, `drule_tests.wl` `List[43, 0]`, `tactics_tests.wl`
  `List[49, 0]`, and printer/parser tests `List[126, 0]`;
- bounded `proptaut_tests.wl` validation, which is green but still expensive
  at about `239s` locally;
- stable snapshot partial validation through
  `scripts/mma-hol-bounded-smoke.sh --mode snapshot`, covering
  `snapshot/build-parser`, `snapshot/run-fast-parser`, and
  `snapshot/extend-proptaut`. The latest refreshed unmodified-clone validation
  was on 2026-06-13 against `mma-hol` HEAD `51bbe9e`.

The known downstream gate is the `Pair.wl` / `Simp` path. Full `run_all.wls`
and full `build_snapshot.wls` are still important, but they should not be
handled by speculative breadth work. Resume them through bounded probes after
the Pair/Simp performance gate is reopened with fresh evidence.

Stable snapshot support is a developer-workflow requirement for the migration.
Strict mode is not a snapshot restore target for `rum`, and `DumpSave` is a
rum textual snapshot format rather than Wolfram `.mx` compatibility.

## Jupyter Tech Preview

The Jupyter lane is now a `rum-host`-backed basic Notebook tech preview inside
the `v0.1` boundary. Kernel-facing request handling routes through `rum-host`;
the adapter owns protocol concerns: kernelspec/bootstrap, ZeroMQ/native
transport, signing, wire codecs, message envelopes, IOPub lifecycle, and MIME
bundles.

The basic Notebook acceptance target is:

- one documented deploy path for a real Notebook frontend;
- `kernel_info`, execute, shutdown, inspect, complete, and is-complete;
- code-cell execution with `text/plain` results;
- prints and runtime messages surfaced as Notebook output;
- runtime failures surfaced as Jupyter errors;
- stdin/input-request resume for simple interactive input;
- graceful handling for common unsupported messages.

The current documented local path is the isolated `jupyter_home/` harness:

```bash
scripts/rum-jupyter-home.sh init
scripts/run-bounded.py --timeout 180 -- scripts/rum-jupyter-home.sh kernel-smoke
scripts/run-bounded.py --timeout 180 -- scripts/rum-jupyter-home.sh browser-smoke
```

`kernel-smoke` validates the real `jupyter_client` protocol surface, including
completion, inspection, is-complete, stdin, streams, messages, and failures.
It also validates unsupported-message keepalive behavior for empty
`comm_info_reply`, ignored comm open/msg/close, explicit unsupported
`debug_reply`, and unknown frontend probes. `browser-smoke` validates
JupyterLab plus headless Chromium notebook execution. On 2026-06-13 in the
local setup, `cargo test -p rum-host`, `cargo test -p rum-jupyter`,
`kernel-smoke`, and `browser-smoke` have all passed.

The following stay outside `v0.1` unless deliberately promoted: robust
interrupt/cancel, widgets/comm, debug protocol, rich display updates,
clear-output/update-display semantics, graphics, and broad frontend
compatibility.

## Release Gates

Default local checks for a stabilization cut should include:

- `cargo fmt --check`;
- `cargo test -p rum-runtime`;
- `cargo test -p rum-host`;
- `cargo test -p rum-cli`;
- `cargo test -p rum-jupyter` when adapter behavior is touched;
- `cargo test --workspace` when the local environment can support the native
  adapter tests.

Downstream and oracle lanes are optional unless their surface is being cut:

- use `scripts/mma-hol-bounded-smoke.sh` for bounded `mma-hol` cold and
  snapshot probes;
- use Wolfram oracle checks through the documented local-kernel policy for
  selected same-name semantics, not as a broad unbounded diff;
- keep performance work probe-first, with the same before/after probe used to
  reject negative optimizations.

There is no current cross-engine `<2x` performance release promise. The active
performance obligation is to keep known `mma-hol` gates measurable, bounded,
and tied to real downstream blockers.

## Explicit Non-Goals

These are not `v0.1` commitments:

- full CAS coverage;
- graphics and visualization;
- Wolfram notebook/front-end compatibility;
- Wolfram `.mx` binary compatibility;
- broad file, network, process, or system APIs;
- widgets, comms, debug protocol, and rich Notebook display behavior;
- project-owned Python adapter revival;
- project-owned speculative showcase packages;
- `WLBuiltin/` cleanup or generated builtin inventory work.

Future examples should stay documentation-level until a downstream need makes
the code valuable. For now, `mma-hol` is the showcase-quality pressure test.

## Current Next Gates

The next work inside the boundary is:

- keep this document, `TODO.md`, and the support matrix aligned as contract
  decisions change;
- keep the isolated host-backed `rum-jupyter` Notebook harness green;
- keep the `mma-hol` snapshot lane green on refreshed unmodified clones as rum
  and `mma-hol` evolve;
- close remaining public suspend/resume helper gaps that still affect callback
  loops or host-facing debug/tooling flows. The fold/window tranche is closed;
  remaining concrete families are functional iteration, targeted mapping,
  tensor/string callbacks, and selected debug/tooling helpers;
- reopen the Pair/Simp performance gate only with bounded probes and fresh
  evidence.
