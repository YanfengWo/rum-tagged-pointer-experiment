# v0.1 Acceptance Boundary

Status date: 2026-07-05.

This document is the current stabilization boundary for the first usable
`v0.1` cut. `v0.1` is a kernel and host-contract stabilization cut. It is not
a full CAS release or a polished notebook product.

## Product Boundary

The release target is a programmable symbolic core-language runtime with a
narrow, hardened host API.

The main acceptance surfaces are:

- the documented core-language slice: the language guide (`docs/guide/`) and
  the generated builtin reference (`docs/reference/`);
- the `rum-host` Rust embedding facade for sessions, requests, structured
  outcomes, failures, prints, messages, traces, input requests, inspect,
  completion, and completeness — including the hardening surface:
  interrupt/cancel, wall-clock timeout, panic isolation with session
  poisoning and recovery, `reset()`, snapshot / restore-from-bytes, and the
  capability sandbox (`HostConfig::sandboxed()`);
- `rum-cli` and `rum-repl` as developer tools for loading scripts, running
  probes, and debugging semantics;
- a `rum-host`-backed basic Jupyter Notebook tech preview.

Internal evaluator, matcher, cache, and representation details remain
unstable unless they are exposed through `rum-host`, documented CLI behavior,
or the language documentation.

## Core-Language Contract

Documented behavior is the commitment (see
[testing-strategy.md](./testing-strategy.md)): a behavior is part of the
`v0.1` contract when the guide or reference documents it, and documented
limits bound what is promised. Undocumented behavior is not a release
promise.

New language breadth should be promoted only when at least one of these is
true:

- it closes a gap inside the documented core-language cluster;
- a concrete downstream embedding or package is blocked on it;
- the missing behavior is needed to preserve an existing public host or CLI
  contract.

Resource limits, recursion limits, message behavior, held evaluation,
definition scoping, package loading, and suspend/resume flows are part of the
runtime contract when they affect the public request APIs.

## Jupyter Tech Preview

The Jupyter lane is a `rum-host`-backed basic Notebook tech preview inside
the `v0.1` boundary. Kernel-facing request handling routes through
`rum-host`; the adapter owns protocol concerns: kernelspec/bootstrap,
ZeroMQ/native transport, signing, wire codecs, message envelopes, IOPub
lifecycle, and MIME bundles.

The basic Notebook acceptance target is:

- one documented deploy path for a real Notebook frontend;
- `kernel_info`, execute, shutdown, inspect, complete, and is-complete;
- code-cell execution with `text/plain` results;
- prints and runtime messages surfaced as Notebook output;
- runtime failures surfaced as Jupyter errors;
- stdin/input-request resume for simple interactive input;
- graceful handling for common unsupported messages;
- real interrupt: execute-on-worker with interrupt-to-cancel and
  poison-restart recovery.

The current documented local path is the isolated `jupyter_home/` harness:

```bash
scripts/rum-jupyter-home.sh init
scripts/run-bounded.py --timeout 180 -- scripts/rum-jupyter-home.sh kernel-smoke
scripts/run-bounded.py --timeout 180 -- scripts/rum-jupyter-home.sh browser-smoke
```

`kernel-smoke` validates the real `jupyter_client` protocol surface,
including completion, inspection, is-complete, stdin, streams, messages, and
failures, plus unsupported-message keepalive behavior (empty
`comm_info_reply`, ignored comm open/msg/close, explicit unsupported
`debug_reply`, ignored unknown frontend probes). `browser-smoke` validates
JupyterLab plus headless Chromium notebook execution.

The following stay outside `v0.1` unless deliberately promoted: widgets/comm,
debug protocol, rich display updates, clear-output/update-display semantics,
graphics, and broad frontend compatibility.

## Release Gates

Default local checks for a stabilization cut:

- `cargo fmt --check`;
- `cargo test --workspace` (narrower `-p` runs while iterating; a green
  narrow gate is not a green tree);
- when an evaluation hot path changed: the rum-local performance A/B —
  `scripts/core-language-microbench.sh` on base and candidate builds,
  compared per label with same-tier neighbors checked;
- when memory behavior is in question: `scripts/core-memory-microbench.sh`.

## Explicit Non-Goals

These are not `v0.1` commitments:

- full CAS coverage; floating-point numerics (exact rationals only, by
  design);
- graphics and visualization;
- compatibility with other vendors' products, front ends, protocols, or file
  formats;
- broad file, network, process, or system APIs;
- widgets, comms, debug protocol, and rich Notebook display behavior;
- project-owned Python adapter revival (frozen; a future revival binds to
  `rum-host`);
- project-owned speculative showcase packages.
