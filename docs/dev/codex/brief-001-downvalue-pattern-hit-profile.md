# Brief 001 — Profile the `downvalue-pattern-hit` primitive (diagnostic only)

## Goal

The core-language microbench shows `downvalue-pattern-hit` is the worst
bottom-up primitive at ~`5.18x` WolframKernel (rum `0.00391s` vs WK
`0.000755s` over 1000 iterations on the reference run). This is the Stage 3
"Definition Dispatch" target in `docs/performance-kernel-rewrite-plan.md`.
Before any code change, produce a self-time profile and caller attribution
that say WHERE rum spends the per-call time on a pattern-matched downvalue
hit, plus a one-paragraph mechanism hypothesis. **No source change.** The
deliverable is evidence Claude will use to write the implementation brief.

## Context pointers

- Read `AGENTS.md` (the unmodified-`mma-hol` hard line) and
  `docs/performance-kernel-rewrite-plan.md` (Stages 3-4) first.
- `docs/proptaut-performance-audit.md` describes the profiling method and the
  two reducer scripts.
- Reducers already in repo: `scripts/sample-self-time.py <sample-file> [N]`
  and `scripts/sample-attribute-callers.py <sample-file> <symbol> [N]`.
- Counters: `RUM_PROFILE_EVALUATION_CACHE=1` prints power-of-two checkpoints
  for `evaluate_entries`, `down_value_scans`, `down_value_applications`,
  `stability_checks`, and the call-stability cache reasons.
- The microbench label `downvalue-pattern-hit` is generated by
  `scripts/core-language-microbench.sh`; its statement shape is a
  pattern-defined downvalue applied to a matching argument (`f[x_] := …; f[…]`
  in a timed loop). Read the generated `core-language-microbench.wls` in the
  output dir to get the exact statement.

## Deliverable

1. A minimal standalone probe that runs ONLY the `downvalue-pattern-hit` shape
   in a tight loop long enough to sample cleanly (a few seconds of CPU), built
   from the exact statement in the generated microbench `.wls`. Keep it under
   `/tmp`.
2. A macOS `sample` capture of that probe (release `rum-cli`, profiling env
   OFF), reduced with `scripts/sample-self-time.py` (top ~25 self-time rows)
   and `scripts/sample-attribute-callers.py` for the top 2-3 leaf symbols.
3. A counter run of the same probe with `RUM_PROFILE_EVALUATION_CACHE=1`
   (this run is for counts only, not timing): report
   `evaluate_entries`, `down_value_scans`, `down_value_applications`,
   `stability_checks`, and the call-stability hit/miss reasons, and the ratio
   of `stability_checks` (and `down_value_scans`) to `down_value_applications`.
4. A one-paragraph mechanism hypothesis: what does rum do per pattern-downvalue
   hit that a ~5x gap is consistent with (matcher compile/clone, candidate
   normalization, binding-map construction, owned-tree clone, stability rescan,
   …), naming the specific rum functions from the attribution.

## rum / Rust pitfalls (read twice)

1. Build the release binary first: `cargo build --release -p rum-cli`. Sample
   the release binary, never debug.
2. Profiling env vars OFF for the `sample` capture; ON only for the separate
   counter run. Never mix.
3. `sample` needs a running pid: launch the probe in the background, `sample
   <pid> <seconds> -file <out>`, then wait. The probe must run long enough
   (raise the loop count) that the sample window lands inside the work, not
   startup.
4. The reducers expect a raw `sample` call-graph file; pass the file path as
   the first arg.
5. Do not infer from a killed/timed-out stdout; make the probe COMPLETE and
   print its own `AbsoluteTiming`.
