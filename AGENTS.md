# Agent Guide

This file is the first-stop guide for coding agents working in this
repository. Keep it short and link to the canonical documents instead of
duplicating them.

`CLAUDE.md` is a separate document for the supervising Claude director (role
split, the Codex task-brief workflow, and the authoritative gate). An
executing agent does not need it; follow the brief you were given plus this
guide.

## Project Snapshot

`rum` is an embeddable, sandbox-first symbolic term-rewriting language and
runtime written in Rust. Its surface syntax is in the Wolfram Language family
of notations; its evaluator implements `rum`'s own documented semantics (see
`DISCLAIMER.md`). The product target is a programmable symbolic runtime and
embeddable rule engine, not a notebook UI, a full CAS, or a clone of any
other vendor's product.

The workspace is organized as Rust crates:

- `rum-syntax`: syntax tree, lexer, parser, diagnostics, formatter
- `rum-core`: shared runtime-neutral core values
- `rum-runtime`: the pure kernel — lowering, evaluation, definitions, scoping,
  messages, matching, tracing, host-facing request APIs, and the
  kernel-resident machinery (Part/control/rewrite data layers,
  instrumentation); builtins are registered data, not kernel code
- `rum-stdlib`: the standard library — owns every builtin family's
  implementation and catalog specs, installed into sessions via `install_core`
- `rum-host`: narrow Rust embedding facade over runtime sessions, requests,
  structured outcomes, and resumable input
- `rum-terminal`, `rum-repl`, `rum-cli`: terminal and CLI layers
- `rum-jupyter`: optional Jupyter adapter and transport work

## Testing Policy (hard lines)

1. Tests verify `rum`'s **own documented behavior** — the language guide, the
   generated builtin reference, and the host crates' rustdoc are the
   normative contract. See `docs/testing-strategy.md`.
2. **No black-box differential testing against other vendors' engines.** Do
   not add oracle harnesses, comparison lanes, compatibility matrices, or
   conformance reports — in code, scripts, fixtures, docs, or CI. Do not
   commit outputs generated by third-party engines. This policy is permanent
   (`DISCLAIMER.md` records its history).
3. Performance gates are **rum-vs-rum A/B**: run
   `scripts/core-language-microbench.sh` on the base and candidate builds and
   compare per-label `timings.tsv` rows. A regression on any hot label, or on
   a same-tier neighbor of the target label, is a defect to fix or report.
4. Do not "fix" a failing test by weakening its documented contract; surface
   the conflict instead.

## Development Commands

Use the local Rust toolchain declared by the workspace (`1.85.x`, edition
2024).

```bash
cargo fmt --check
cargo test -p rum-runtime
cargo test --workspace
```

Use focused tests while iterating, then run the broader relevant suite before
handing work back. For runtime semantics work, `cargo test -p rum-runtime` is
the default minimum; cross-crate changes need `--workspace`.

For long-running commands or anything that may spawn child processes, do not
start them bare. Use `scripts/run-bounded.py --timeout SECONDS -- <command>`
(or a repo script that delegates to it); it kills the whole process group on
timeout so no orphaned children are left behind.

## Code Organization Rules

Follow [docs/code-organization-guidelines.md](./docs/code-organization-guidelines.md).
The practical thresholds are:

- under `10k` chars: preferred
- `10k` to `20k`: warning range
- `20k` to `35k`: split-plan range
- over `35k`: architecture debt unless explicitly documented

Prefer real module boundaries over arbitrary cuts. Split by responsibility:
syntax vs lowering, evaluation vs matching, planning/normalization vs
rendering/mutation, transport vs codec vs backend, and so on.

**Safe Rust is a hard convention.** `rum-core` and `rum-runtime` are
ZERO-`unsafe` (verified; the only `unsafe` in the repo is the off-by-default
alloc-count `GlobalAlloc` in `rum-cli`). Do not introduce `unsafe` into the
kernel crates — there is almost always a safe equivalent at the same cost
(e.g. `Option<Arc<…>>` niche-packs to `Arc<…>`'s size and gives a safe
`.take()` for a manual `Drop`). If you believe `unsafe` is unavoidable, STOP
and surface it for a decision rather than shipping it.

**Hot-path changes are measured, not asserted.** A change touching an
evaluation hot path (eval/dispatch/matcher, `Expr`/`SharedExpr`/`SharedArgs`
construction or `Drop`, candidate-value lookup) must be gated with a
`scripts/core-language-microbench.sh` base-vs-new A/B — a "no default-path
cost" intention is not evidence; an O(N) cost hidden inside a "fast path"
only shows up when measured.

The timing suite uses in-kernel `AbsoluteTiming` backed by Rust's monotonic
`Instant`. Never difference the wall clock, and do not make timing decisions
while another CPU-heavy workload is running. The benchmark scripts run in the
normal workspace sandbox; timing is not a reason to request elevated execution.
Native ZeroMQ tests skip automatically when loopback access is unavailable.

**No default-path cost for diagnostics.** Counters and instrumentation go
behind the env-gated cold-load `AtomicU8` pattern; a `Mutex`, allocation, or
branch paid on every call when the flag is off is a regression.

## Working Rules

- Keep tests near the crate that owns the behavior: `rum-runtime`/`rum-stdlib`
  tests own language semantics, `rum-host` tests own the embedding lifecycle,
  adapter/protocol behavior stays in the adapter crate.
- Do not check in generated build artifacts or temporary probe files.
- **`rum` source files use the `.rum` suffix — including generated and
  throwaway ones.** Scripts that emit `rum` code to run (benchmark sources,
  scratch probes under `/tmp`, fixtures) name it `*.rum`, never `.wls` or
  `.wl`. The suffix is a labelling convention rather than a runtime
  requirement — the interpreter ignores it — but `rum` has diverged from the
  Wolfram Language in documented ways, so a Wolfram suffix on a file we
  generate ourselves implies a compatibility claim the project does not make
  (`docs/guide/getting-started.md` §suffix, `DISCLAIMER.md`). Referring to a
  *third-party* file by its real name (e.g. an external suite's
  `run_all.wls`) is correct and unaffected.
- Preserve user changes in a dirty worktree. Never revert unrelated edits just
  to make a patch easier.
- Prefer small, reviewable commits with messages that state the semantic or
  organizational change (when the workflow has you commit at all — Codex
  briefs leave the tree uncommitted for the gate).
- When behavior documented in the guide/reference changes intentionally,
  update the documentation in the same change; the reference drift test will
  fail otherwise.
